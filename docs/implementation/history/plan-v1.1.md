## 4. 小步骤执行循环与输出控制

1. 定位：读RUN、当前任务卡和相关指令/契约/代码，不重读所有历史。
2. 选择：确定一个可验证子目标，优先解除主路径的契约、构建、安全阻塞。
3. 实施：直接改文件，默认每次1～3个相关文件或短patch，大功能按自然边界分块落盘。
4. 验证：跑覆盖本次变化的必要检查，失败先修，不把问题堆到最终阶段。
5. 记账：保存步骤、证据、阻塞、下一动作，按原任务验收更新父状态。
6. 继续：会话资源足够且有可执行动作就继续，不以“下一步可以……”代替实施。

1～3文件是初始软阈值，不是拆碎代码或截断源码的硬要求。大文件先写完整可运行骨架，再按完整函数/组件迭代；每次写入保持结构完整。依赖锁由对应工具生成，不在聊天逐行输出。

| 类型 | 默认做法 | 避免 |
| --- | --- | --- |
| 进展 | 持续工作约每45～60秒一句事实更新 | 长时间无状态，或反复长篇解释 |
| 回合总结 | 约150～300字：任务、文件、验证、阻塞、下一步 | 全源码、长diff、整份计划、全96项清单 |
| 读取 | rg定位后读相关片段，初始每次约80～150行 | 全仓cat、node_modules、所有历史日志 |
| 命令结果 | 成功报摘要；失败先看关键错误和末尾约40～80行 | 几千行构建/依赖日志进入对话 |
| 大资源 | 写文件，引用路径和摘要 | base64、整个图集/模型、大型JSON |
| 长命令 | 记录运行信息后启动，增量观察 | 超时后重复启动同一构建或下载 |

上述字数/行数是本方案执行约定，不是官方产品额度或保证不重连的阈值。必要错误、验收问题和用户决定不得为省字隐瞒。长日志留存前去除秘密；供应key、令牌、私人内容不写状态或提交仓库。

## 5. 重连、上下文压缩与换会话后的恢复

先读项目指令和RUN，核对工作区及未结束命令，再读当前任务卡。不能把聊天“已完成”当唯一事实。

- 未提交修改：辨认用户和本次修改后继续，不破坏性重置、不覆盖。
- 命令可能仍运行：核对命令、目录、PID及启动时间/运行ID；PID会复用，不能仅凭数字判断。不要重复启动；无可查结果记未确认，做最小必要验证。
- 状态落后代码：依据文件补记，不回滚代码去配旧状态。
- 状态领先代码：仅将相关验收改为待核验，补缺失小步，不把全计划归零。
- 半成品：补齐当前子步骤再检查，不重写整个模块。
- 缺断点：依据原任务、工作区和少量相关证据重建执行索引，不重建产品。

恢复后马上继续具体动作，不重写一份长分析。上下文压缩时同样显式读断点，不假设历史记忆完整保留。

## 6. 尽快完成项目的推进方法

### 6.1 复用成果，减少重复成本

先核对已有A～F成果，复用工程、依赖锁、组件、端口和测试，只补缺口；不为新目录重做可用模块。领域、契约、令牌、状态机与共享UI维护一套；系统捕获/浮层/通知/存储/媒体安全出口仍按平台分别实现。

FS须前置完成；SS允许前置启动且所需输入可用后开展；FF可先做准备，最终验收不能早于相关前项。不能按编号盲目串行，也不能把SS理解成无条件同时修改共享文件。

在工具允许时，并行独立读取、静态检查和确定性测试；争用同一数据库、端口、设备、锁文件、构建目录或可变状态的操作串行。默认一个写入负责人，共享契约和依赖锁集中修改。未经用户明确授权多代理时，采用单代理连续执行，不自行开多会话并发改仓库。
